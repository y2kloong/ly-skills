# Commit 分析总结

## 输出定位

本 skill 的总结是给**测试人员（非开发人员）**看的，描述一律采用**业务语言**：

- 用"哪个页面、哪个操作、改动前是什么样、改动后用户会看到/被阻止了什么"来表述改动，而不是文件路径、方法名、接口地址、字段/变量名、组件名等代码细节。
- 让测试人员一眼就能看出：**改了哪部分功能、对业务有什么影响、该怎么测**。

## 触发方式

仅通过指令调用：

```
/ly-tb-commit-summary <commit-id>
```

例如：`/ly-tb-commit-summary 1144cde1bc0119bc358f53d88b3d4f206d3a9e27`

可以一次传入多个 commit ID（空格分隔）。

## 输出模式选择（仅多个 commit 时需要）

**单个 commit ID**：直接按"逐条总结"输出，无需询问。

**多个 commit ID**：先用 AskUserQuestion 询问用户选择哪种输出模式，得到明确答复后再进行分析输出：

- **逐条总结**：按 commit ID 数量输出对应个数的分析块，每个 commit 一个独立分析块（各自包含 修复方案 / 业务影响分析 / 转测试建议）。
- **合并总结**：将多个 commit 合并为一个分析块输出（多个 commit 属于同一功能、同一修复链、可整体测试时通常选此项）。

参考询问内容：

```
question: 本次提供了 3 个 commit ID，希望如何总结？
header: 输出模式
options:
  - label: 逐条总结
    description: 每个 commit 单独输出一个分析块（3 个 commit → 3 块），便于逐个核对。
  - label: 合并总结
    description: 多个 commit 合并为一个分析块，适合属于同一修复链条、可整体测试的场景。
```

若合并前发现多个 commit 主题差异较大、不属于同一功能链，可在询问时提示"逐条总结可能更合适"，但仍以用户选择为准。

## 工作流程

### 第一步：获取 commit 信息

对每个 commit ID 执行：

```bash
git show <commit-id> --format=full --stat
```

需要关注的信息：
- commit message（问题描述）
- 修改了哪些文件
- 具体 diff 内容

### 第二步：确认输出模式

- 传入 1 个 commit ID：跳过此步。
- 传入多个 commit ID：按上文"输出模式选择"用 AskUserQuestion 询问，确认是逐条总结还是合并总结。

### 第三步：分析并输出

按所选输出模式输出对应格式（见"输出格式"）。输出前，把从 diff 里读到的代码细节（文件路径、方法名、接口、字段、组件、列 ID 等）**翻译成业务语言**再落笔。

## 测试视角写作规范

写「修改内容」和「业务影响分析」时，必须遵守：

1. **不暴露代码细节**：不直接写文件路径（src/...）、方法名、接口地址、字段/变量名、组件名、低代码列 ID 等。
2. **用业务语言表述改动点**：以"哪个页面 → 哪个操作 → 改动前是什么样 → 改动后用户会看到/遇到什么"来描述。
3. **行为差异优先**：优先说清楚用户可见的变化（新增了提示、禁止了某个操作、某数值自动带出、校验时机前移等）。
4. **涉及后端时业务化**：如需后端配合，写"依赖后端新增的迁移校验能力"这类表述，不写具体接口地址。
5. **「修改页面」一行用业务菜单路径**：如 GTM总部→商品管理→...→XX查询页；文件路径仅作开发追溯用，放在括号里可省略。
6. 「修改内容」的改动点用业务功能名做小标题，不写代码细节、不附行数统计。

## 输出格式

### 格式一：逐条总结（每个 commit 一个分析块）

严格使用以下格式，确保方便复制（不使用表格）：

```
## 提交 <短hash> 分析总结

**提交信息：** <commit message 的简短描述>

**修改页面：** <业务菜单路径，如 GTM总部→商品管理→销售信息管理→XX查询页>（附：<文件路径> 供开发追溯，可省略）

---

### 1. 修复方案

**根因：** <一句话说明问题原因（业务语言）>

**修改内容：**

- **<改动点1标题（业务功能名）>**：<用业务语言描述改动后的用户可见行为，如"XX页的'变更'操作新增校验：点击变更时先判断该数据是否处于迁移/移交中，是则弹提示并禁止进入变更页">
- **<改动点2标题>**：<改动说明>

**思路：** <整体修复思路总结（业务语言）>

---

### 2. 业务影响分析

<站在测试角度，用业务语言描述影响范围、改动前后行为差异、对用户的影响、风险点、兼容性，不使用表格>

---

### 3. 转测试建议

<用编号列表列出测试要点，每个要点包含场景 → 预期结果>
```

多个 commit 逐条总结时，每个分析块之间用 `---` 分隔。

### 格式二：合并总结（多个 commit 合并为一个分析块）

```
## 合并总结（共 N 个提交）

**提交信息：**
- <短hash>：<commit message 简短描述>
- <短hash>：<commit message 简短描述>

**修改页面：**
- <业务菜单路径>（<功能说明>）
- <业务菜单路径>（<功能说明>）

---

### 1. 修复方案

**根因：** <多个 commit 共同针对的问题或需求的一句话说明（业务语言）>

**修改内容：**

- **<按业务功能/页面分组的改动点标题>**：<该组涉及哪些提交、改了什么（业务语言）>
- **<改动点标题>**：<改动说明>

**思路：** <整体修复思路总结（业务语言）>

---

### 2. 业务影响分析

<用业务语言描述合并后的影响范围、正向影响、风险点、兼容性，不使用表格>

---

### 3. 转测试建议

<用编号列表列出测试要点，每个要点包含场景 → 预期结果；若多个 commit 属同一功能链，可整体联测>
```

合并总结要点：
- 修改页面按"共用逻辑（如同一校验能力被多个页面复用）"与"各自页面"分组说明。
- 转测试建议优先整体联测，再补各 commit 特有场景。

## 示例

以下是一个标准输出示例（逐条总结，注意「修改内容 / 业务影响分析」均为业务语言，无代码细节）：

```
## 提交 1144cde1 分析总结

**提交信息：** 修复选装包组合中填写"小订组合优惠力度"后不能自动带出"小订组合优惠价"的问题

**修改页面：** GTM总部→商品管理→销售信息管理→车型→选装包组合编辑弹窗

---

### 1. 修复方案

**根因：** 原逻辑只在保存时计算"组合优惠价"，编辑过程中输入"组合优惠力度"不会实时触发计算。

**修改内容：**

- **实时联动计算**：在"组合优惠力度"输入合法且"组合官方价"已填写时，立即自动带出"组合优惠价"（组合官方价 - 组合优惠力度），无需等保存后才显示。
- **输入校验增强**：对"组合优惠力度"增加有效性校验，非法值（为空、非数字、负数等）不触发计算。
- **清空兜底**：当"组合官方价"或"组合优惠力度"无效、或优惠力度为 0 时，清空"组合优惠价"，避免残留旧值。

**思路：** 借助表单实时校验机制，在输入过程中即时触发联动计算，让用户在保存前就能看到组合优惠价，减少等待和反复保存。

---

### 2. 业务影响分析

影响范围仅限 GTM 总部→商品管理→销售信息管理→车型→选装包组合编辑弹窗。

用户填写"组合优惠力度"后能即时看到组合优惠价，交互体验提升，无需保存后二次确认。

实时计算依赖输入校验：若"组合官方价"未填时填写优惠力度，不会触发计算（符合预期）。当优惠力度为 0 时会清空优惠价——需确认业务上是否允许优惠力度为 0 的场景。

纯前端改动，不影响后端接口，不影响已有数据。

---

### 3. 转测试建议

1. 正向流程：先填"组合官方价" → 再填"组合优惠力度" → 确认"组合优惠价"实时自动计算且值正确。
2. 反向流程：先填"组合优惠力度" → 再填"组合官方价" → 确认"组合优惠价"也能自动带出。
3. 边界值：优惠力度为 0 时确认清空行为是否符合业务预期；优惠力度等于官方价时优惠价应显示 0；输入非法值不触发计算。
4. 修改场景：已有优惠价后修改官方价或优惠力度 → 确认联动更新。
5. 保存验证：确认保存后数据与实时显示一致。
```

## 注意事项

1. 如果 commit 只改了 1 行，直接说明改了什么，不需要强行拆分多个改动点。
2. 「修改内容 / 业务影响分析」面向测试人员，一律用业务语言，不暴露文件路径、方法名、接口地址、字段名、组件名等代码细节。
3. 「修改页面」指的是业务菜单路径（从大到小，如 GTM总部→商品管理→...），不是代码路径；文件路径仅供开发追溯。
4. 转测试建议要具体、可执行，包含边界值和回归场景，不要写泛泛的"测试一下功能"。
5. 全文不使用 markdown 表格，方便用户直接复制到文档中。
6. 传入多个 commit ID 时，必须先询问输出模式（逐条 or 合并），不得擅自决定；单个 commit 无需询问，直接输出。
