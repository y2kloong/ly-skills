# Commit 分析总结

## 触发方式

仅通过指令调用：

```
/ly-tb-commit-summary <commit-id>
```

例如：`/ly-tb-commit-summary 1144cde1bc0119bc358f53d88b3d4f206d3a9e27`

可以一次传入多个 commit ID（空格分隔），逐个分析。

## 工作流程

### 第一步：获取 commit 信息

对每个 commit ID 执行：

```bash
git show <commit-id> --format=full --stat
```

需要关注的信息：
- commit message（问题描述）
- 修改了哪些文件
- 具体 diff 内容

### 第二步：分析并输出

按以下固定格式输出，每个 commit 一个分析块。

## 输出格式

严格使用以下格式，确保方便复制（不使用表格）：

```
## 提交 <短hash> 分析总结

**提交信息：** <commit message 的简短描述>

**修改文件：** <文件路径>（<功能说明>）

---

### 1. 修复方案

**根因：** <一句话说明问题原因>

**修改内容（+X 行，-Y 行）：**

- **<改动点1标题>**：<改动说明>
- **<改动点2标题>**：<改动说明>

**思路：** <整体修复思路总结>

---

### 2. 业务影响分析

<用自然段落描述影响范围、正向影响、风险点、兼容性，不使用表格>

---

### 3. 转测试建议

<用编号列表列出测试要点，每个要点包含场景 → 预期结果>
```

## 示例

以下是一个标准输出示例：

```
## 提交 1144cde1 分析总结

**提交信息：** 修复选装包组合中填写"小订组合优惠力度"后不能自动带出"小订组合优惠价"的问题

**修改文件：** `OptionGroupEditModal.vue`（选装包组合编辑弹窗）

---

### 1. 修复方案

**根因：** 原来只在保存时计算"组合优惠价"，编辑过程中输入"组合优惠力度"不会实时触发计算。

**修改内容（+16 行）：**

- **新增 `isValidNumber` 方法**：校验值是否为有效的非负数，排除 null、undefined、空字符串和非数字。
- **在校验回调中增加实时计算**：当"组合优惠力度"输入合法且"组合官方价"已填写时，立即计算 组合优惠价 = 组合官方价 - 组合优惠力度。
- **扩展官方价的 change 处理**：当"组合官方价"变化时，若价格或优惠力度无效或为 0，清空"组合优惠价"。

**思路：** 在表单校验回调中挂入计算逻辑，利用 Element Plus 表单的实时校验机制触发联动计算。

---

### 2. 业务影响分析

影响范围仅限 GTM 总部→商品管理→销售信息管理→车型→选装包组合编辑弹窗。

用户填写"组合优惠力度"后能即时看到组合优惠价，无需等保存后才显示，交互体验提升。

实时计算依赖输入校验，若"组合官方价"未填时填写优惠力度，不会触发计算（符合预期）。当任一值为 0 时会清空优惠价——需确认业务上是否允许优惠力度为 0 的场景。

纯前端改动，不影响后端接口，不影响已有数据。

---

### 3. 转测试建议

1. 正向流程：先填"组合官方价" → 再填"组合优惠力度" → 确认"组合优惠价"实时自动计算且值正确。
2. 反向流程：先填"组合优惠力度" → 再填"组合官方价" → 确认"组合优惠价"也能自动带出。
3. 边界值：优惠力度为 0 时确认清空行为是否符合业务预期；优惠力度等于官方价时优惠价应显示 0；输入非法值不触发计算。
4. 修改场景：已有优惠价后修改官方价或优惠力度 → 确认联动更新。
5. 保存验证：确认保存后数据与实时显示一致。
```

## 注意事项

1. 如果 commit 只改了 1 行，直接说明改了什么，不需要强行拆分多个改动点。
2. 业务影响分析要说明影响的具体页面路径（从大到小，如 GTM总部→商品管理→...）。
3. 转测试建议要具体、可执行，包含边界值和回归场景，不要写泛泛的"测试一下功能"。
4. 全文不使用 markdown 表格，方便用户直接复制到文档中。
5. 如果 diff 涉及多个文件，按文件分组说明改动。
6. 如果用户一次给了多个 commit ID，逐个分析，每个之间用 `---` 分隔。
