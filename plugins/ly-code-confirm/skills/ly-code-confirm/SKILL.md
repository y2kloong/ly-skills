# 代码确认管控表生成

## 背景

在组件版本管控 / 跨版本代码归属确认场景中，需要把一批组件/文件路径逐一查其 git 历史，
整理成一张《代码确认管控》表格：每个组件归属哪个需求/TB 号、当前版本是否包含、由谁管控/确认。
本技能把这一整套查历史 + 组表逻辑固化为一个脚本，避免每次手工查询和填表。

## 通用性

脚本是**纯 Node 实现、零第三方依赖**（不依赖 exceljs / 不需要 npm install）：
- 跨项目、跨语言可用——前端 JS/Vue、后端 Java/Python/Go/Rust 等项目都能跑；
- 只要目标机器装了 Node 即可，与项目技术栈无关；
- 业务口径（ticket 正则、编码有效期天数、作者映射、项目经理默认值（默认空）、文件名、history 条数、表头、测试组长预设映射
  `CONFIG.testLeadMap`）全部集中在脚本顶部 `CONFIG` 常量中，跨项目时改一处即可。

## 触发方式

**仅能通过 `/ly-code-confirm` 指令手动调用**，绝不在任何用户消息内容上自动触发。
调用时用户随指令提供路径列表，例如：

- `/ly-code-confirm` 后跟整段粘贴的路径（每行一条）
- `/ly-code-confirm <path1> <path2> ...`（命令行参数）
- 指令 + 指向一个保存了路径列表的文件

如果用户只输入了 `/ly-code-confirm` 而没有给出任何路径，**必须向用户索要路径列表**，不要空跑。

## 工作流程

### 第一步：收集路径列表

把用户提供的路径整理成"每行一条"的列表。要求：
- **1:1 原样保留**用户给的路径，不遗漏、不省略、不改写大小写/分隔符。
- 若用户给的是文件（如 txt/日志），读取该文件内容作为路径来源。

### 第二步：查询"模块版本管控人"清单

将路径列表写入**系统临时目录**下的一个文件（每行一条，文件名带上本次用途避免并发冲突），
然后**进入用户当前所在的项目目录**，先用 `--list-managers` 让脚本只输出会出现的"模块版本管控人"清单
（不生成表格）：

```bash
cd "<用户当前项目目录>"
node "C:\Users\lyhuliuhao\.claude\skills\ly-code-confirm\scripts\generate_code_confirm.cjs" --list-managers < "<临时文件>"
```

输出形如：

```
Managers: ["彭君","邬凡"]
ManagerCount: 2
```

这些就是"模块版本管控人"列（取需求编号所用那条 history 的提交人，按下方"提交人名称规范化"映射展示）。

### 第三步：交互补全"项目经理"与"模块测试组长/测试主担"

**先问"项目经理"**：这张表所有行的项目经理都是同一个值，用 `AskUserQuestion` 一次性问用户
"这列填什么"，提供「我来填写姓名」/「留空」两个选项，由用户填写具体姓名。

- 用户给了姓名 → 记为项目经理值，调用脚本时用 `--pm "<姓名>"` 传入。
- 用户选择"留空" → 用 `--pm ""` 传入，整列留空。
- 未询问或未传 `--pm` 时，脚本该列**留空**（`CONFIG.defaultPM` 默认为空字符串，不回退任何预设姓名）。

**再问"模块测试组长/测试主担"**：拿到第二步的管控人清单后，**必须用 `AskUserQuestion` 逐个（或一次性）询问用户**：
每个"模块版本管控人"对应的"模块测试组长/测试主担"是谁。

- 把第二步得到的每个管控人都问一遍，问题文本带上管控人姓名，方便用户对照填写。
- 如果某个管控人用户回答"不知道 / 跳过 / 留空"，就把它当作空值（该列留空），不要编造姓名。
- 拿到答案后，整理成 `模块版本管控人=模块测试组长/测试主担` 的映射，写入**临时目录**下的映射文件
  （每行一条，`#` 开头为注释）：

```
彭君=张三
邬凡=李四
```

### 第四步：调用生成脚本

**仍在用户当前所在的项目目录**，把路径列表重定向到 stdin，并用 `--test-lead-map` 传入第三步的映射文件、
用 `--pm` 传入第三步问到的项目经理：

```bash
cd "<用户当前项目目录>"
node "C:\Users\lyhuliuhao\.claude\skills\ly-code-confirm\scripts\generate_code_confirm.cjs" --pm "<项目经理>" --test-lead-map "<映射文件>" < "<临时文件>"
```

需要显式指定输出目录时追加 `--out-dir <目录>`；映射条目很少时也可不用文件，直接
`--test-lead "彭君=张三" --test-lead "邬凡=李四"`（分隔符支持 `=`、`：`、`:`，多种方式可叠加，后面的覆盖前面的）。

脚本会自动做以下事情：
- 对每个路径执行 `git log -3`（取前 3 条 history；无 git 或路径不存在则返回空）。
- 按下方"表格口径"填充每一行，生成 `代码确认管控_yyyyMMdd_HHmmss.xlsx`（带时分秒，
  同一天多次生成也不会互相覆盖）。
- 用 `--pm` 的值填充"项目经理"列；未传 `--pm` 时该列留空（`CONFIG.defaultPM` 为空字符串，不回退任何预设姓名）。
- 用 `--test-lead-map` / `--test-lead` 提供的映射填充"模块测试组长/测试主担"列；
  未提供映射的管控人，该列留空并在输出里提示 `ManagersWithoutTestLead: ...`。
- 若目标文件正被 Excel 占用（EBUSY），自动追加 `_v2`、`_v3`… 重试，不会覆盖用户打开的旧表。
- 输出 `Total: <数量>, with empty history: <数量>`、`Managers: [...]`、
  （如有）`ManagersWithoutTestLead: ...` 和最终写入路径。

**输出位置解析顺序**（脚本内自动完成）：
1. `--out-dir <目录>` 参数（或环境变量 `CODE_CONFIRM_OUT_DIR`）——显式指定，优先级最高；
2. **用户桌面目录**（默认）：Windows 经 Known Folder 查询（兼容 OneDrive / 目录重定向），
   查询失败时回退 `USERPROFILE\Desktop`、`USERPROFILE\OneDrive\Desktop`；其它平台取 `~/Desktop`；
3. 以上都没有 → 脚本输出 `NO_PROJECT_ROOT` 并以退出码 2 结束。

> git log 的查询目录与输出目录相互独立：脚本仍先在**当前 git 仓库根 / 最近的工程标记目录**里执行 `git log`，
> 但表格文件默认写到**桌面**，不会写入仓库内污染工程目录。

**如果脚本输出 `NO_PROJECT_ROOT`**（未检测到桌面目录，也未显式指定输出位置），**必须用 `AskUserQuestion` 询问用户要把 Excel 保存到哪里**，拿到目录后用 `--out-dir` 重跑：

```bash
node "...\generate_code_confirm.cjs" --out-dir "<用户指定的目录>" < "<临时文件>"
```

### 第五步：核对输出

生成后**必须**向用户汇报，并快速核对（脚本输出是机器填充，需人工抽查兜底）：

1. **路径数量**：Excel 行数 == 用户提供的路径数。
2. **空 history 的组件**：若 `with empty history > 0`，列出这些路径并提醒用户——
   它们通常是新增/未跟踪文件，需求编号与版本管控人为空，需要人工补充。
3. **抽样抽查取值**：挑 1-2 个路径用 `git log -3 --format="%an|%at|%s" -- "<路径>"` 人工核对，
   确认"需求编号"列与脚本规则一致（尤其 NIPTV 提取 / 编码 commit 已超过 2 周而兜底最新 message 两种情况）。

### 第六步：汇报结果

向用户报告：
- 输出文件完整路径（以脚本输出的 `Written: <完整路径>` 为准，默认位于**桌面**；显式 `--out-dir` 时位于用户指定目录）。
- 总共多少条路径、多少条空 history（如有，逐条列出，提示需人工补）。
- 抽查结论（哪个路径取了 NIPTV 号、哪个是兜底最新 message）。

## 表格口径（必须严格遵守）

| 列 | 取值规则 |
|----|----------|
| 路径 | 用户提供的 1:1 路径 |
| 是否属于当前版本 | 默认「是」 |
| 代码对应的需求编号或磐石问题号或TB号(或增加改动原因） | 见下方"需求编号规则" |
| 项目经理 | 第三步交互中由用户指定（`--pm "<姓名>"`）；用户选择留空或未询问/未传时整列为空（不回退任何预设值） |
| 模块版本管控人 | 取"需求编号"所用那条 history 的**提交人**（作者名规范化见下） |
| 模块测试组长/测试主担 | 由用户在第三步交互中给出（键为"模块版本管控人"的映射）；用户未提供的管控人该列留空 |
| 差异确认人 | 与模块版本管控人一致 |
| 确认日期 | 运行当天，格式 `yyyy/mm/dd` |

### 需求编号规则（核心）

对每个路径取**前 3 条** `git log`（`git log -3`，同时取每条的提交时间）：

1. 若前 3 条中**有** commit message 匹配 `NIPTV-\d+`，且**最新那条命中 commit 与最新一次提交
   的时间间隔不超过 2 周（14 天）**：取这条含 NIPTV 的 commit，
   只提取其中的 NIPTV-编码（如 `NIPTV-162743`；同一 commit 含多个则用顿号「、」连接，如 `NIPTV-139289、NIPTV-139290`），
   其它 message 内容不要。
   - **过期例外**：若这条带编码的 commit 距最新一次提交已超过 2 周，说明编码对应的需求已经很旧，
     此时**不再取该编码**，改为取最新一次提交的完整 message（即走第 2 条）。
2. 若前 3 条中**没有** NIPTV，或命中的 commit 已超过 2 周：取最新一次提交的**完整** message 作为该列值。

> 注意：
> - 是「前 3 条」而不是前 5 条——这是与早期版本的重要差异，务必保持一致。
> - 「2 周」的判定用每条 commit 的提交时间（脚本取 `%at`，即作者提交时间戳）；阈值可在脚本
>   `CONFIG.ticketStaleDays`（默认 14）中调整。
> - 「模块版本管控人」/「差异确认人」始终跟随最终取值的那条 commit（取编码就跟随编码 commit，
>   过期兜底就跟随最新 commit）。

### 提交人名称规范化

`模块版本管控人` / `差异确认人` 取的是 git 作者名，需做映射：
- `ly-pengjun` → **彭君**
- `ly-wufan2` → **邬凡**
- 其它作者名原样保留（如 胡柳浩、钟伟亮、刘湖水、邓佩云、刘泽明、何怿铭 等）。

> 新增映射改脚本 `CONFIG.authorMap`；这里列出的键是"模块版本管控人"清单（第二步输出）里可能出现的值。

## 常见边界情况

- **路径不存在 / 无 git 历史**：该行需求编号与版本管控人留空，`是否属于当前版本` 仍为「是」，
  汇报时单独列出提醒人工补（该行也没有管控人，不参与第三步交互，测试组长/测试主担列同样留空）。
- **第二步清单为空**（所有路径都没有 history，常见于新增/未跟踪文件或非 git 项目）：
  没有需要询问的管控人，跳过"模块测试组长/测试主担"的提问，但**仍要问项目经理**，
  然后用空映射生成表格。
- **用户对某个管控人回答"跳过 / 不知道"**：该管控人对应的"模块测试组长/测试主担"留空，
  **绝不编造姓名**；生成后提示用户该列仍需人工补齐。
- **用户对项目经理回答"留空 / 跳过"**：整列留空（`--pm ""`），不要回填任何默认姓名。
- **非 git 项目**（检测到工程标记但没有 git）：表格能正常生成，但所有路径的"需求编号/模块版本管控人"
  都为空（没有 git history 可查），生成后明确告诉用户这两个字段需要人工填写。
- **默认输出到桌面**：Excel 默认生成在用户桌面（Windows 兼容 OneDrive 重定向），方便取用；
  如需保存到别处，用 `--out-dir` 指定。
- **检测不到桌面目录**（且未指定 `--out-dir` / `CODE_CONFIRM_OUT_DIR`）：脚本输出 `NO_PROJECT_ROOT`，
  必须询问用户保存位置并用 `--out-dir` 重跑。
- **输出文件被 Excel 占用**：脚本会自动写 `_v2`/`_v3` 等后缀，汇报时告知用户实际文件名即可。
- **无 Node 环境**：提示用户安装 Node 后重跑（脚本是纯 Node，不依赖任何第三方包）。
- **路径含空格**：必须通过 stdin 文件传入（每行一条），不要用命令行参数传含空格路径。
- **管控人名含分隔符**：映射条目按第一个 `=`/`：`/`:` 切分，管控人姓名本身不要包含这些字符。
- **并行调用冲突**：同时跑多个本技能时，临时路径文件、映射文件都用唯一命名（如带时间戳），避免互相覆盖。

## 重要约束

1. **只显式触发**：未输入 `/ly-code-confirm` 绝不自动执行。
2. 路径必须 1:1 保留，任何情况下不得"补全"或"纠错"用户给的文件路径。
3. 需求编号只取前 `CONFIG.historyLimit`（默认 3）条 history 中的 ticket；命中编码的 commit
   距最新提交超过 `CONFIG.ticketStaleDays`（默认 14 天）时必须改取最新一次提交的完整 message，
   不要只按"有编码就取编码"处理。
4. 生成后必须核对并汇报，尤其空 history 的组件要提醒用户人工补充。
5. **"项目经理"和"模块测试组长/测试主担"都必须来自用户**：第三步一定要先问用户，
   绝不能自己猜测/编造姓名；用户选择留空的列就留空（项目经理不会被默认值悄悄填上）。
6. 跨项目使用时如 ticket 编号体系、默认人员、文件名不同，改脚本顶部 `CONFIG` 常量，不要改业务逻辑本身。
